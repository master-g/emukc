# Resource History and Cosmetic Seasons - Plan

让玩家在任意时间看到过去某个季节的立绘、台词和立绘坐标（「春天过圣诞」）。分两层：

- **L0 资源历史**：缓存不再原地覆盖，按（路径，版本）记下每次拿到的内容。同时做两件省流量的事：版本号升了但文件没变时不重新下载；记下 `Last-Modified` 与大小。
- **L1 外观季节**：全局配置选一个季节，`getData` 换上那时的 `api_mst_shipgraph`，资源请求按版本号取当时的内容。

**基线**：`main` `bb6a00d3`。

## Evidence（2026-10-15 实测，2026-10-14 维护前后）

- **CDN 只保留每个文件的当前版本。**
  - `?version=` 只用来绕过缓存，53、54 或不带，拿到的都是同一个对象。
  - 节日立绘是在原路径上换内容。吹雪 `ship/full/0009_5991_gyckjmemgqoe.png`：本地 2026-09-20 下载的是 173,982 B，CDN 现在是 107,837 B，`Last-Modified` 2026-10-14。
- **CDN 不给 hash。**
  - 没有 `ETag`，也没有 MD5 之类的头，只有 `Last-Modified`、`Content-Length`、`Accept-Ranges`。
  - 支持 `If-Modified-Since`：时间相同返回 304、0 字节；早 1 秒返回 200 和全文。
  - 同一文件在不同节点上的 `Last-Modified` 不同，w01y 与 w05o 相差 18 秒到 2 分 35 秒。所以不能拿一个节点的时间去另一个节点做条件请求。
- **版本号升了、内容没变很常见。**
  - `version.json` 的 `item` 6.3.1.0→6.3.6.0：`item_common.png` 的 `Last-Modified` 是 2023-11-28，`item_menu_1.png` 是 2018-08-17，只有 `item_ilist_pumpkin.*` 是 2026-10-14。
  - 吹雪立绘版本 59→60：20 个舰船文件里只有 `full`、`full_dmg` 变了，其余 18 个仍是 2018 年的。
- **一个季节的规模**（kcwiki start2 `5214c06b4c`(09-20) 对 `a8e8e47b3b`(10-15)）：
  - 立绘：195 艘的 `api_version[0]` 升了，其中 174 艘的坐标字段也变了。
  - 台词：64 艘的 `api_version[1]` 升了。曙 27 条里换了 2 条（10-14），另有 2 条是 09-10 换的。
  - 母港台词：865 艘的 `api_version[2]` 一起从 910 升到 1014。
  - 合计：立绘约 400 张，单张 100–170 KB。
- **只看修改时间会多判。** 对上面四类候选文件逐个 HEAD（4,673 个）：
  - 1,339 个的 `Last-Modified` 是 10-14：立绘 386/390、台词 137/2,553、母港台词 816/1,730。另有 7 条台词在 CDN 上已经 404。
  - 把 1,339 个都下下来比 sha256：内容真的变了的有 672 个（立绘 380、台词 131、母港台词 161），其余 667 个是原样重传（立绘 6、台词 6、母港台词 655）。
  - 这次大小单独就完全区分开了：大小变了的全部内容不同，大小没变的全部内容相同。
  - 所以「时间变了」不等于「内容变了」。不比时间只比大小，这 667 个都可以不下；但大小相同、内容不同理论上可能出现，样本只有这一次。
- **快照只是「那天的样子」，不能直接当成「常规版」或「某个节日版」。**
  - 10-14 换上的立绘混着几个主题：吹雪是祭典法被，多摩 #100 是万圣节猫斗篷，白露 #42 是秋装。
  - 09-20 的缓存里已有上一季的节日装：多摩是浴衣，白露是和服。曙有 2 条台词是 09-10 换的。
  - 也有舰在 10-14 换回了常规版。
  - 図鑑的 `character_full`（常规立绘的缩小版，431×645）可以当参照，但自动判断不可靠：
    - 09-20 的 183 艘里，111 艘颜色差值 < 5，确定是常规版；约 55 艘 ≥ 30，确定是节日版；其余约 20 艘要人工看。
    - #348 的万圣节版是同款衣服换色，差值 12.3，比常规版 #390 的 17.0 还低。
  - 两个日期都穿节日装的舰，我们手上没有它们常规版的 `full`，只能等官方换回时再存。
  - 两份快照在 `z/seasons/2026-09-20/`（维护前，1,346 个，含 7 条已从 CDN 删掉的台词）和 `z/seasons/2026-10-14/`（1,339 个）。各有 `manifest.json`，记路径、版本、大小、sha256，后者另记 `Last-Modified`。
- **过去的季节从官方拿不回来。**
  - 客户端図鑑只加载 `card`、`character_full`、`character_up`（`ShipDetailContent`），不含季节立绘。
  - fandom 的季节立绘是裁掉透明边的版本（461×1017，游戏原图如 750×1320），没法原样下发。en.kancollewiki 有 Cloudflare 人机验证。
- **元数据有历史。** 我们用的 `kcwiki/kancolle-data` `api/api_start2.json` 从 2019-06-15 起有 122 份快照，过去的版本号和坐标都能取到。
- **现状代码**：
  - `kache_entry` 只存 path→version（`emukc_cache/src/kache.rs:21`）。
  - 拿到新版本就原地覆盖（`emukc_network/src/download.rs:373`）。
  - 请求旧版本时给本地较新的文件（`kache.rs:268`）。
  - `getData` 原样下发码典里的 start2（`api_start2/mod.rs:13`）。
  - 没有任何季节或游戏时钟的概念。

## Decisions

- **季节就是某个日期的状态**，用日期命名，比如 `2026-10-14`。「常规版」「万圣节 2026」之类的名字是给日期加的人工标签，不让程序去推断。
- **季节由全局配置决定（用户定）**，所有玩家看到同一个季节；不配置时就是当前官方状态。
- **活文件树不动。**
  - `z/cache/<path>` 仍是「当前版本」，现有工具（headless、清单对拍、mods）照常读。
  - 历史内容另存在内容寻址的 blob 目录（sha256）里，相同内容只存一份。
- **一个文件在版本 v 时的内容 = 记录里版本不超过 v 的最新那条。**
  - 版本升了但内容没变，也记一条（同一 hash），这样任何版本都查得到。
  - 版本 v 早于所有记录时，给最早那条。
- **版本号天然唯一**，不同季节的 URL 不会撞上浏览器缓存，不需要另编版本号。季节 A 下发 59、当前是 60，浏览器把它们当作两个地址。
- **刷新判断只看大小（用户定）。**
  - 版本号升了先 HEAD：`Content-Length` 与记录相同就只记新版本号（同一 hash），不下载。
  - `Last-Modified` 照样记下，留作证据，不参与判断。
  - 没有记录时照旧整份下载。
  - 已知风险：大小相同、内容变了会漏掉。2026-10-14 的 1,339 个文件里没有这种情况。
- **季节清单手工维护（用户定）**，放在 `crates/emukc_bootstrap/assets/seasons.json`：日期 id、人工标签、对应的 kcwiki start2 提交。在 CLAUDE.md 的手工维护例外名单里登记。快照文件本身只在各人本地。
- **季节替换只碰 `api_mst_shipgraph`**，按舰逐条替换 `api_version` 与坐标字段。那个季节之后才有的舰保持当前。

## Not in scope

- **L2 补回 2026-10 之前的季节**：缺原始文件。以后有人提供当年的原始缓存，可用 U4 的导入。
- **L3 季节玩法**：限定任务、兑换、限定掉落、家具限时贩卖、活动海域。兑换界面写死在 `main.js` 里，一个客户端版本只认一年的版本，这是硬上限。
- **母港 BGM、其他季节性 UI**：尚未调查。

## Open questions

- 已结：刷新判断只看大小；季节清单放 `assets/seasons.json`（均为用户定）。
- 已结：`api_version[2]` 一次升了 865 艘，对应的 1,730 个文件里只有 161 个内容变了，大多是只升号、不换文件。

## Implementation Units

- **U1（先写测试）**：`emukc_cache` 加 blob 目录和历史表，键为（path, version），值为 sha256、大小、`Last-Modified`、取得时间。
  - 覆盖活文件前，先把旧内容收进 blob。
  - 旧的 `kache_entry` 保留，只读迁移。
- **U2（先写测试）**：按「版本不超过 v 的最新记录」取内容，替换 `kache.rs:268` 的「给更新的那份」规则。没有历史时行为不变。
- **U3（先写测试，本地 HTTP 夹具）**：版本升了先 HEAD，按大小判断要不要下载；同时记录 `Last-Modified`。
- **U4**：CLI `cache archive import <dir> --version-from <start2>`，导入 2026-10-15 的保护快照。另加一个可选的批量 HEAD 回填 `Last-Modified` 的命令（只取响应头）。
- **U5**：季节定义。
  - 从 kcwiki 指定提交取 start2，只存 `api_mst_shipgraph` 到 `.data/seasons/<id>.json`。
  - 季节清单 `assets/seasons.json`，先登记 `2026-09-20`、`2026-10-14` 两条。
- **U6（先写测试）**：配置项选季节。`getData` 按 U5 替换 shipgraph 条目。端到端检查：headless 截母港立绘，对比两个季节。
- **U7**：`docs/solutions/` 记缓存历史与季节的语义；CLAUDE.md 命令表补 U4/U5 的命令。
