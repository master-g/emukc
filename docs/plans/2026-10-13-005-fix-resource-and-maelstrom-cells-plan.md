# Resource and Maelstrom Cells - Plan

Issue #96。出撃走到资源点（`event_id` 2）与渦潮（`event_id` 3）时，数量与种类都是占位算法：资源点是
「舰数 × 10 + (`cell_no` % 5) × 3」，种类按 `color_no` 选；渦潮固定 30%、无上限、按 `color_no == 4` 选弾薬。

## Evidence

- 地图目录里资源点的 `color_no` 是 56 个 2、2 个 6、1 个 8，渦潮 30 个全是 3：现在 56 个资源点给燃料，
  渦潮全掉燃料。
- wikiwiki 七个海域页（2026-10-13 取）逐格写了资源点的种类与区间、渦潮的种类、基本喪失割合与喪失上限値；
  `資材` 页有汇总表、渦潮的算式与两个算例、強うずしお 的格子。53 个资源点格子有 52 个，25 个渦潮全有。
- 7-4 O 取自 zekamashi「７－４－O(港マス)」：ドラム缶 +8／+6、内火艇 +7／+10、上限 200／120。两组实例
  （内火艇 4 + ドラム缶 2 → 84／72；内火艇 9 + ドラム缶 2 → 119／120）反推出基数 40／20。
- 大発系的范围取 wikiwiki `装備最大値/大発系装備早見表/テーブル` 的「資源マス」列。
- 客户端（`main.decoded.js`）：`DropItemModel` 在 `api_usemst` 4 时用 `[-1,31,32,33,34,2,1,3,4][api_icon_id]`，
  即 1–4 是四种基本资源、5 高速建造材、6 高速修復材、7 開発資材，与 `MaterialCategory` 同号；`api_usemst` 5
  时 `api_icon_id` 就是 useitem 的 id。`HappeningModel` 用同一张表查 `api_mst_id`，现在发的是 0。
- 客户端只在護衛退避时调 `goback_port`；普通的撤退与打完回港都只调 `api_port/port`。

## 取舍

- **数据放在地图目录上的一张侧表**（`MapCatalog`，按海域 id 与 `cell_no`），不往格子结构上加字段：格子的
  字面量有 82 处。资产按「海域名 + 节点标签」写，组装地图目录时落到 `cell_no`，对不上的条目是组装错误。
- **基本资源在母港视图入账，页面重载则作废。** 普通撤退与正常回港在服务器看来都只是一次 `port`，所以待入账
  的数量记在出撃存储里、不随出撃状态一起清掉，母港视图的前置结算把它入账。中途刷新页面时客户端会先请求
  `require_info`（只在启动流程里请求），`require_info` 视图把待入账的数量丢掉。
- **区间内按 5 的步长均匀抽**；来源只说「5刻み」。
- **強うずしお 取 10%**；来源写「1割ほど」。
- **缺数据的兜底**：4-4 D、7-3 K、7-3 L 按燃料 30%、无上限；「確認不可能」的上限按无上限；带「?」的区间
  按印出的数字。资产里逐条标 `guess`。
- **1-6 的「大発動艇搭載数」按整个大発系算**，与别的格子同一个数法；来源没有说只算 68 号。

## Implementation Units

- **U1 资产与组装。** `map_cell_effects.json`（手工维护）进 `REPO_ASSETS`；组装地图目录时挂到侧表；
  测试：每个 `event_id` 2 与 3 的格子恰好有一条（1-6 G 的 `event_kind` 是 4，也算）。重建 codex。
- **U2 资源点的种类与区间。** `next_sortie` 在 1-2 B 发弾薬、10–20、5 的倍数。
- **U3 装备加成、式子型格子、一格多项。** 通用加成、5-4 I、5-5 E、1-6、3-5 J、7-4 O。
- **U4 特殊资材与家具箱。** 当场入账；投影层的 `api_usemst`／`api_icon_id`。
- **U5 基本资源回港入账。** 出撃途中不动司令部资材，母港视图入账一次。
- **U6 渦潮。** 每格的种类、割合、上限，強うずしお，报文取最大的一艦并修正 `api_mst_id`；四个直调内部
  函数的旧测试迁到 `next_sortie`。
- **U7 文档。** `docs/solutions/architecture-patterns/` 沉淀；`CLAUDE.md` 禁止文件段加例外；drift 基线。

## 实施记录

- 出撃的第一格是资源点或渦潮时（1-2 B、2-2 A、5-1 A 等）原先完全不结算：`start_sortie` 不调结算，投影层把
  `api_itemget`／`api_happening` 写死成空。这次一并结算。
- 1-6 G 的 `event_kind` 是 4，原先的结算遇到非 0 就返回，所以它什么都不给。现在按「地图目录里有没有设定」
  判断，不看 `event_kind`。
- 渦潮报文的 `api_mst_id` 原先发 0，客户端的表查到 -1；现在发 1／2。`api_type` 照字段清单发 1。
- 喪失割合在资产里是整数百分比，算式全用整数（`残量 × 割合 × (100 − 减免) / 10000`），避免浮点取整。
- 强渦潮的上限：来源在两种都量到的格子上数值相同（1-3 H、3-3 F、6-2 D），所以每格只记一个上限。
- 3-3 C 的上限，`資材` 页的算例写 30、海域页写 40；取海域页（`資材` 页自己说以各海域页为准）。
- drift-check 的清单与基线加了 `map_cell_effects`。接受基线时 `kcnav_enemy_fleets` 的指纹也跟着换了：它在
  这次改动之前就与基线不一致（资产文件本身这次没动）。来源已查清：`199a7d73` 与 `1ab7c55d`（2026-10-09，
  基地空袭的敌方编成）改了资产而没有刷新基线，改动是有意的。

## Risks

- 资源点与強うずしお 各多抽一次随机数，只在这两类格子抽。带种子、路过这类格子的测试序列会移位：换种子，
  不放宽断言。golden 若动了，有意重冻并说明。
- 改了资产或组装后要 `cargo run -- bootstrap --codex-only`，否则测试读到旧的地图目录。
